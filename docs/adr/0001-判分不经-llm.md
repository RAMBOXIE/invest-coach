# ADR-0001：判分与 LLM 的关系

- 日期：2026-08-26
- 状态：已裁决

## 两条规则，不要混为一谈

| | 规则 | 状态 |
|---|---|---|
| ① | **事实不出自 LLM** —— 真实公司数字、准则条文、官方认定只能来自原档取数管线（EDGAR accession + 行号 → `facts.json` → 人工核定）。LLM 只解释已核定的材料 | **铁律** |
| ② | **判分不经 LLM** —— 对错由前端确定性规则给 | **推迟，不是禁止** |

① 是产品的立身之本（可靠、可溯源）。② 是工程选择。

## ② 为什么现在仍然这么做

不是禁令，是三条现实收益：

- **离线可用** —— 没有后端、断网、超时，判分照常。这是单文件交付形态的一部分
- **零延迟** —— 答完立刻出反馈，不等一次网络往返
- **可复现** —— 同一份答案永远得到同一个判分。做不到这点，勘误台账就无从谈起

质问台的语义路由不受影响，它本来就不是判分：LLM 的全部输出是一个证词 id，
文本一律取自 `case.json`（见 LLM_USE_REGISTRY #8）。

## 要引入 LLM 判分，先满足这些

排在最前的是**它能解决而规则引擎解决不了的那个问题**：
现在只能判选择题，判不了「用你自己的话说出你的推理链」。那才是 step-based 教学的终点。

1. **只判开放文本，不动选择题的判分。** 规则引擎那条路不许被替换
2. **判分理由必须可回放** —— 存下 prompt、rubric、模型输出，用户能看到「为什么这么判」。
   做不到可回放就不上
3. **先做成不计分的第二意见**（「教练还看到了这些」）。判分影响 Brier 校准分与锚题点亮，
   跑一段时间再谈计分
4. **离线降级路径** —— 没有后端时开放题怎么办，要有明确答案
5. `validate.py` **R19 的工程锁**（内容里出现 `llm` / `judge` 字段即 ERROR）**暂时保留**。
   它挡的是「悄悄把判分接进 LLM」，不是挡这条设计路线。真要做时连同这条锁一起改，
   并在本 ADR 补一节说明改成了什么
